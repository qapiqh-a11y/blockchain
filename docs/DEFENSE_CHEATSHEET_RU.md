# Быстрые ответы для защиты

## 1. Что делать, если компрометация admin key реалистична?

Не держать все полномочия на одном EOA. Разделить роли, использовать multisig для admin, timelock/двухэтапную передачу административных прав, минимизировать DEFAULT_ADMIN_ROLE, мониторить RoleGranted/RoleRevoked и иметь emergency-процедуру. В OpenZeppelin для более строгой admin-модели существуют AccessControlDefaultAdminRules и AccessManager.

## 2. Почему одного ReentrancyGuard недостаточно?

ReentrancyGuard блокирует конкретный повторный вход, но безопасная архитектура должна минимизировать окно риска. Checks-Effects-Interactions означает: сначала проверки, затем изменение внутреннего state, и только потом внешний вызов. Тогда даже при передаче управления внешнему коду состояние уже приведено в согласованный вид. Также остаются cross-function/cross-contract и бизнес-логические риски.

## 3. Что такое автоматически проверяемый invariant?

Это точное свойство, которое должно быть истинно после любой допустимой последовательности операций и которое можно выразить как boolean/assertion. Например: `Revoked ticket never becomes Validated`. Функциональное требование описывает конкретный сценарий («validate изменяет Created→Validated»), invariant ограничивает все возможные сценарии.

## 4. Ограничения Slither

Slither хорошо находит известные code patterns, но не знает реальный бизнес-смысл ticket validation, внешние trust assumptions и требования организации. Он может давать false positives и пропускать логические ошибки. Поэтому отсутствие critical findings не является доказательством безопасности — нужны threat modeling, unit/fuzz/invariant tests и ручной review.

## 5. Как доказать, что fix устраняет root cause?

Повторить атаку тем же и вариативными входами, проверить security invariant и regression suite. В нашей работе vulnerable version доверяет `tx.origin`; fixed version вообще убирает эту модель и использует `msg.sender` через AccessControl. Поэтому блокируется класс неавторизованных промежуточных callers, а не один конкретный calldata/адрес attacker.

## Дополнительные вопросы

**Почему хранится dataHash, а не документ?** Публичный Ethereum не обеспечивает конфиденциальность. Hash позволяет позже проверить целостность защищённой off-chain записи.

**Зачем две роли?** OPERATOR меняет ticket state, AUDITOR выполняет аудит; разделение полномочий уменьшает последствия компрометации одного account.

**Почему tx.origin опасен?** Он отражает исходный EOA всей call chain и не меняется при промежуточных contract calls. Поэтому вредоносный contract может вызвать victim от имени origin в логике, которая ошибочно считает origin авторизацией.

**Почему AccessControl лучше самописного if?** Он предоставляет стандартную role-based модель, grant/revoke, events и общепринятый механизм проверки `msg.sender`.
